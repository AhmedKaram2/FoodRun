Physical-device acceptance, mobile distribution and the production rollout are not established by these local checks.

## Result

The core order lifecycle uses the same server rules across the three clients. This pass corrected web state/history/payment discrepancies, selected-orderer permissions and added shared quantity shortcuts, automatic delivery and clearer payment actions. Automated suites and both native builds pass. Full platform parity is **not yet established**: the remaining differences and verification limits below are part of the audit result.

## Remaining differences and follow-up verification

1. **Localization:** finish the remaining dynamic/secondary validation and status messages, then run native RTL and large-text walkthroughs. Core strings and web RTL were checked; complete Arabic coverage is not claimed.
2. **Offline acceptance:** web now archives up to 200 own receipts in account/hub-scoped IndexedDB and caches the app shell for read-only access. No tokens, bank details or other people’s receipts enter that archive; logout/account changes request deletion. Browser storage is not encrypted. Pure projection tests, synthetic IndexedDB isolation/deletion and production shell reload with the preview server stopped passed. A real signed-in offline reload remains to be exercised.
3. **Menu authoring:** web library and admin now share guided sizes/extras editing. Native uses the existing simple editor and import schema for advanced menus; guided authoring UI is not identical across platforms.
4. **Live device acceptance:** repeat an authenticated web + Android + iOS meal on a local hub and on the internet, including refresh/reconnect, background notifications, selected-payer acceptance, edits, adjusted totals, reimbursement/refund and next order. Automated controller/server coverage does not establish OS/network behavior.
5. **Distribution:** the source push is authorized. Android/iOS binaries have not been released; live deployment and download availability require separate verification. Render is configured to deploy on source commits, so a successful push does not by itself prove a successful rollout.
6. **Web delivery size resolved:** administration, restaurant library, menu editor and offline receipts load separately; Firebase and React use separate chunks. The main chunk is about 261 kB minified / 64 kB gzip and no chunk triggers the 500 kB warning.

## Business flow and payment example

The owner chooses the restaurant or runs the poll, shares the room and starts selection. Everyone, including the selected person, can add/modify food before review. The selected person shares their receiving details, collects the combined order, places it and records paying the full restaurant bill. Members then pay that person immediately or return to the balance in their wallet later. Sender declaration leaves the balance outstanding; recipient approval settles the declared amount. The owner is not the recipient unless selected.

For three members with food, delivery is allocated as AED 1.67, 1.67 and 1.66 using stable member-ID rounding, totaling exactly AED 5. For six members, each pays AED 1. The chosen person's own share is included in the restaurant bill but excluded from reimbursements to themselves. Archived/manual-fee records are not silently repriced.
